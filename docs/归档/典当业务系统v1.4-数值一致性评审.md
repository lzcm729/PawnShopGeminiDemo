### 1. 强制违约赔偿基数：设计文档与代码三方不一致

**问题**: 强制违约的赔偿金计算在设计文档、代码逻辑、UI 显示三处使用了不同的基数，导致玩家看到的数字、实际扣除的数字、设计预期的数字可能完全不同。

**分析**:

| 来源 | 赔偿公式 | 勋章案例 (principal=$3500, valuation=$3500, realValue=$50000) |
|------|----------|-------------------------------------------------------------|
| 设计文档 (Section C) | "200% **估值**" | $3500 x 2 = $7,000 |
| 代码 `usePawnShop.ts:36` | `principal * 2.0` | $3500 x 2 = $7,000 |
| UI `ExpiryEventModal.tsx:16` | `valuation * 2` | $3500 x 2 = $7,000 |
| 经济参数文档 | "200% 估值的2倍" | 歧义 |

表面上看三者数值可能一致（因为当前 `valuation` 通常等于 `principal`），但语义完全不同：

- **principal** = 实际放出的当金（玩家给客户的现金）
- **valuation** = 合同上的估值基准（`pawnInfo.valuation`，在 `useGameEngine.ts:722` 中被设为 `pawnAmount` 即 principal）
- **设计文档说"200% 估值"** = 意图是基于物品估价，但估价本身在系统中有多个含义（perceivedValue? realValue? 合同 valuation?）

当前代码中 `valuation === principal`，所以暂时没有 bug。但如果未来 valuation 和 principal 分离（例如合同估值高于实际放出的当金），三处就会产生不同结果。

**建议**: 在设计文档中明确定义赔偿基数为 `principal`（当金）还是 `perceivedValue`（玩家看到的估值），并统一三处实现。从设计意图看，用 `principal` 作为基数更合理（你赔的是你拿走别人东西的代价，以你给出的金额为基准），但文档应显式声明。

**严重程度**: :red_circle: 高 -- 数值定义歧义是经济系统的定时炸弹

### 2. 利息计算公式存在三种不同实现

**问题**: 同一个"包干制利息"概念在代码中有三种不同的计算方式，会导致不同场景下利息数值不一致。

**分析**:

| 代码位置 | 公式 | 7天/10%利率/$1000本金 | 14天/10%利率/$1000本金 |
|---------|------|----------------------|----------------------|
| `usePawnShop.ts:22` (正式赎回) | `principal * rate * (effectiveDays / 7)` | $1000 x 0.1 x 1 = **$100** | $1000 x 0.1 x 2 = **$200** |
| `useGameEngine.ts:843` (自动赎回) | `principal * (1 + rate)` | $1000 x 1.1 = **$1100** (总额) | $1000 x 1.1 = **$1100** (不考虑期限!) |
| `useFinancialProjection.ts:94` (财务预测) | `principal * rate` | $1000 x 0.1 = **$100** | $1000 x 0.1 = **$100** (不考虑期限!) |
| `ExpiryEventModal.tsx:17` (续当利息UI) | `principal * rate` | $1000 x 0.1 = **$100** | $1000 x 0.1 = **$100** |
| 经济参数文档 | `本金 x 利率 x 期限(天) / 7` | $1000 x 0.1 x 7/7 = **$100** | $1000 x 0.1 x 14/7 = **$200** |

关键不一致：

1. `useGameEngine.ts:843` 的自动赎回使用 `principal * (1 + rate)` 是完全错误的公式，它把利率当成了一次性比例而非周利率，且完全忽略了期限。一个 14 天期限的交易和 7 天期限的交易利息完全相同。
2. `useFinancialProjection.ts:94` 的财务预测也忽略了期限因子 `termDays / 7`，导致预测值系统性偏低（14天合同被低估一半）。
3. 只有 `usePawnShop.ts:22` 正确实现了完整的包干制利息公式。

**建议**: 将利息计算统一到一个共享函数（可以复用 `usePawnShop.calculateRedemptionCost` 的逻辑），消除三处独立实现。设计文档中的公式 `本金 x 利率 x 期限(天) / 7` 是权威来源。

**严重程度**: :red_circle: 高 -- 直接导致玩家在不同界面看到不同利息数值，且自动赎回时收益计算错误

### 3. 声誉惩罚数值在设计文档与代码之间不一致

**问题**: 强制违约/恶意买断的声誉惩罚数值，设计文档和代码实现存在显著差异。

**分析**:

| 行为 | 设计文档 (Section E) | 代码实现 (`inventoryReducer.ts`) |
|------|---------------------|-------------------------------|
| 强制违约 (HOSTILE_TAKEOVER) | 人情 -30, 信誉 -20, 黑道 +10 | 信誉(Credibility) -50, 人情(Humanity) -20 |
| 违约赔偿 (RESOLVE_BREACH) | (未明确定义) | 信誉(Credibility) -50 |
| 拒绝续当 (REFUSE_EXTENSION) | 人情 -10 | 人情(Humanity) -10 |

具体差异：

1. **信誉惩罚**: 设计文档写 -20，代码实现 -50。代码惩罚是设计的 2.5 倍，在初始值 50 的情况下一次违约直接归零触发 Game Over。
2. **人情惩罚**: 设计文档写 -30，代码实现 -20。方向相反，代码反而更宽松。
3. **黑道/清白**: 设计文档写黑道 +10，但代码中声誉系统已从"黑道"改为"清白"（声誉系统 v2.0），设计文档仍引用旧轴名。
4. **RESOLVE_BREACH** 仅扣信誉不扣人情，但按设计意图（"你私自卖了别人的东西"），人情损失应该更大。

**建议**:
1. 将设计文档 Section E 更新为使用新的三轴名称（人情/商誉/清白）
2. 统一数值。建议基于代码当前的惩罚力度重新评估：-50 信誉在初始 50 分的情况下会直接归零，是否符合设计意图？如果是"一次违约直接结束游戏"的设计，需要明确声明。
3. 补充 RESOLVE_BREACH 的完整声誉影响定义。

**严重程度**: :red_circle: 高 -- 声誉系统是生存机制（归零 = Game Over），数值偏差直接影响游戏难度和可玩性

### 4. 声誉系统"不可能三角"在日常交易中的矩阵不完整

**问题**: 设计文档 Section F 的到期结算声誉影响与声誉系统文档 v2.2 存在数值冲突，且与实际代码也不一致。

**分析**:

**赎回场景 (REDEEM):**

| 选项 | 典当业务文档 | 声誉系统文档 | 代码实现 |
|------|-------------|-------------|---------|
| 同意赎回 | 人情+3, 信誉+2 | (未单独列出) | (需确认) |
| 拒绝赎回 | 人情-30, 信誉-20, 黑道+10 | (属于强制违约) | 信誉-50, 人情-20 |

**续当场景 (RENEW):**

| 选项 | 典当业务文档 | 声誉系统文档 | 代码实现 |
|------|-------------|-------------|---------|
| 同意续当 | +当期利息, 人情+5 | (属于"逾期宽限": 人情+1, 商誉-1) | 无声誉变化 |
| 拒绝续当 | 人情-10 | (属于"严格执行": 商誉+1, 人情-1) | 人情-10 |

两份文档对续当的声誉处理截然不同：
- 典当业务文档认为同意续当是大善举（人情+5）
- 声誉系统文档认为宽限逾期只是小善（人情+1）且要扣商誉（-1）

同意赎回的人情+3也令人困惑——这只是履行合同义务，为什么会获得如此高的人情奖励？对比声誉系统日常矩阵中标准交易仅+1。

**建议**: 以声誉系统 v2.2 为权威来源统一数值。同意赎回作为基本义务不应给大量声誉奖励（建议 0 或信誉+1），同意续当可以给人情+1~2。

**严重程度**: :yellow_circle: 中 -- 声誉获取膨胀会破坏三轴平衡的核心设计

### 5. 绝当变现比例 (80% realValue) 对 HIGH uncertainty 物品的经济影响缺乏联动

**问题**: 经济参数文档定义绝当变现比例为 `realValue * 80%`，代码中 `sellActivePawn` 也使用 `realValue * 0.8`。但鉴定系统 v1.3 的方向 C（流当变现偏差）定义了基于 uncertainty 的偏差范围 `[-30%, +10%]`，两套机制如何叠加没有说明。

**分析**:

当前代码 (`usePawnShop.ts:332`) 使用固定的 80% 变现率，完全没有实现鉴定系统 3.4 节描述的 uncertainty 偏差机制。假设未来实现后叠加：

| uncertainty | 基础变现 | 偏差范围 | 最终变现范围 | 期望变现 |
|-------------|---------|---------|------------|---------|
| LOW | 80% | [0, 0] | 80% | 80% |
| MEDIUM | 80% | [-10%, +5%] | 70%~85% | 78% |
| HIGH | 80% | [-30%, +10%] | 50%~90% | 70% |

问题在于：
1. 卖绝当品用 100% realValue（`sellForfeitItem`），而违约出售用 80% realValue（`sellActivePawn`）。绝当品为何比违约出售更值钱？从设计角度，绝当品已归玩家所有可以慢慢卖，违约出售是"急售"才打折，这是合理的。但设计文档没有解释这个区别。
2. 鉴定精度偏差应该作用于哪个变现路径？如果只作用于绝当变现（100%路径），那 HIGH uncertainty 下期望从 100% 降到 90%，变动幅度很小。如果作用于违约出售（80%路径），最差情况 80% x 70% = 56%，变动很大。

**建议**: 在设计文档中明确两种变现路径（违约出售 vs 绝当出售）的基础比例和 uncertainty 偏差的叠加方式。建议偏差作用于绝当出售路径（因为那是玩家真正需要评估风险的场景）。

**严重程度**: :yellow_circle: 中 -- 影响鉴定系统 ROI 的核心感知，但当前未实现不会立即出问题

### 6. 包干制利息在续当场景下的经济失衡

**问题**: 设计文档 Section B 和 Section F 对续当利息的定义存在经济漏洞。

**分析**:

根据设计：
- 首次签约：利息 = 本金 x 利率 x 期限/7（包干制）
- 续当时：玩家收取"当期利息"，延长 7 天

代码 (`ExpiryEventModal.tsx:17`) 中续当利息 = `principal * interestRate`（即一周利息）。

`usePawnShop.ts:84-98` 中 `processExtension`：收取由 `calculateRedemptionCost` 计算的完整利息，然后将 dueDate 延长 7 天。

问题是 `calculateRedemptionCost` 在续当时计算的利息是**从签约日到当前日的全部利息**（包干制），而不是仅仅一周的续当利息。假设一个 7 天期限、10% 利率的合同到期续当：

```
首次签约利息 = principal * 0.10 * 7/7 = principal * 0.10 (已包含在赎金中)
续当时 calculateRedemptionCost 算出的利息 = principal * 0.10 * 7/7 = principal * 0.10
```

看起来一致，但如果是 14 天期限的合同在第 14 天到期续当：
```
calculateRedemptionCost 利息 = principal * 0.10 * 14/7 = principal * 0.20
```

玩家在续当时收了两周的利息——但 UI 只显示一周的利息（`principal * rate`）。UI 显示和实际收取金额不一致。

更重要的是，从 NPC 视角，续当意味着"多给我 7 天，我先付利息"。如果收取的是从签约日开始的全部利息而非仅一周利息，NPC 等于在为已经过去的时间重复付费（包干制下首次赎回就会付全额利息）。

**建议**: 续当利息应固定为一周利息 `principal * rate`（或根据续当延长天数计算），而非重新计算全部利息。UI 和逻辑需要对齐。

**严重程度**: :red_circle: 高 -- 续当场景下玩家可能看到的金额和实际收取金额不同

### 7. 每日客户数 = 4 时的 AP 经济压力测试

**问题**: 经济参数文档写每日最大客户数为 1，但 `game.toml` 配置为 4（1 叙事 + 3 填充）。AP 上限 10 是否足以支撑 4 个客户的鉴定 + 议价需求？

**分析**:

每位客户的 AP 消耗预算：

| 操作 | AP消耗 | 次数（保守） | 小计 |
|------|--------|-------------|------|
| 鉴定 | 1/次 | 2次 | 2 AP |
| 耐心消耗 | 间接 | - | 0 AP |
| 议价推拉 | 0 AP | - | 0 AP |

4 位客户 x 2 AP = 8 AP，剩余 2 AP 作为缓冲。

但在以下情况下会超支：
- 高价值物品需要 3-4 次鉴定才能达到 LOW uncertainty（0.30 x 0.85^n < 0.10 需要约 7 次）
- 鉴定意外"客户不耐烦"（额外耐心-1）间接迫使减少鉴定次数
- 夜间格物消耗的是精力而非 AP，所以不冲突

极端场景：如果 4 位客户中有 2 位带高价值物品需要充分鉴定（各 4 次），加上 2 位普通客户（各 1 次），总共 10 AP 恰好用完。但没有任何容错空间。

**建议**: 数值上 10 AP / 4 客户是可行但紧张的。建议在经济参数文档中补充 AP 预算分析表，明确设计意图：是希望玩家"每个都仔细看"还是"选择性深入"。如果是后者，当前数值合理；如果是前者，AP 需要上调到 12-14。

**严重程度**: :green_circle: 低 -- 当前数值在设计空间内，但应明确记录设计意图

### 9. 场景三（贪婪捕食）的 ROI 计算验证

**问题**: 设计文档的经典示例——勋章值 $50,000，赔偿 $7,000——需要验证在当前数值体系下是否成立。

**分析**:

场景假设：
- 老兵典当勋章，玩家给出当金 $3,500
- 玩家通过鉴定发现真实价值 $50,000
- 设计文档说"赔偿金只需 $7,000"

按当前代码实现：
- 赔偿 = `principal * 2` = $3,500 x 2 = **$7,000** -- 与文档一致
- 绝当后变现 = `realValue * 1.0` = **$50,000** (FORFEIT 状态 100% 变现)

**净利润分析**:
```
强制违约利润 = 变现收入 - 赔偿金 = $50,000 - $7,000 = $43,000
正常赎回利润 = 赎金(本金+利息) - 0 = $3,500 + $350(10%/7天) = $3,850
利润倍数 = $43,000 / $3,850 = 11.2x
```

从纯经济角度，强制违约的收益是正常赎回的 **11 倍**。搭配的惩罚是：
- 代码：信誉-50（直接归零触发 Game Over），人情-20
- 设计文档：人情-30, 信誉-20, 黑道+10

如果按设计文档的惩罚值（信誉-20），玩家从 50 降到 30，不会触发 Game Over。这意味着玩家可以通过 1-2 次标准交易（各+1信誉）慢慢回血，同时坐拥 $43,000 利润。这是否是预期的平衡？

按代码实现（信誉-50），一次违约直接 Game Over，那么这个选项实际上永远不可选——除非玩家已经通过大量标准交易把信誉堆到 50 以上。

**建议**:
1. 如果设计意图是"高风险高回报的终极赌博"，惩罚应该足够重但不应一击致死。建议信誉 -25~-30（降到危险区但不归零），同时加上清白影响。
2. 如果设计意图是"几乎永远不应该做"，当前代码的 -50 足以实现，但应在文档中明确说明。
3. 无论哪种设计，文档和代码必须对齐。

**严重程度**: :yellow_circle: 中 -- 核心道德困境的经济平衡直接影响游戏核心体验

### 10. 续当利息收入在包干制下的经济意义分析

**问题**: 设计文档说"续当时玩家收取利息"，但在包干制利息框架下，续当利息的经济定位不清晰。

**分析**:

包干制利息的核心是"签约时利息锁死，提前赎回不减少利息"。那么续当是否意味着"重新签约一周并收取额外利息"？

两种解读：

**解读 A**: 续当 = 续费模式（收新利息 + 延长）
```
首次合同：7天，本金$1000，利率10% → 利息$100
续当：+7天，收取新利息 $100 → 总利息收入 $200
最终赎回：本金$1000 + 第二期利息$100 = $1100
玩家总收入：$200（两期利息）+ $1000（本金）= $1200，净利润 $200
```

**解读 B**: 续当 = 利息先付模式（先收原利息，延期后正常赎回）
```
首次合同：7天，本金$1000，利率10% → 利息$100
续当时：先付原期利息$100 → 延期7天
最终赎回：本金$1000 + 新期利息$100 = $1100
玩家总收入：$100 + $1100 = $1200，净利润 $200
```

两种解读的净利润相同，但现金流不同。解读 A 更有利于玩家（提前回收部分利润）。

代码 (`processExtension`) 的行为是解读 B：`calculateRedemptionCost` 计算全期利息并收取，然后延长 dueDate。但正如发现 #6 指出的，这里的利息计算可能不正确。

**建议**: 在设计文档中明确续当的经济模型：玩家收到什么、NPC 支付什么、新赎回价是什么。建议采用简单明确的模型："续当时 NPC 支付一周利息 (`principal * rate`)，新赎回价 = 本金 + 一周利息（新包干）"。

**严重程度**: :yellow_circle: 中 -- 续当场景虽然不频繁，但经济语义不清会导致玩家困惑

### 11. 违约出售 (sellActivePawn) 的净利润可能为负

**问题**: 违约出售以 80% realValue 变现，但如果玩家之前给出的当金（principal）高于 80% realValue，净利润为负。

**分析**:

违约出售的完整成本：
```
净利润 = 变现收入 - 当金(已付给客户) - 赔偿金(客户来赎时)
       = realValue * 80% - principal - principal * 200%
       = realValue * 0.8 - 3 * principal
```

盈利条件：`realValue * 0.8 > 3 * principal`，即 `principal < realValue * 0.267`

如果玩家给出的当金超过物品真实价值的 26.7%，违约出售就是亏本的。考虑到正常议价中当金通常是 perceivedValue 的 50-80%，而 perceivedValue 通常接近 realValue，违约出售在绝大多数情况下是**严重亏损**的。

但这可能正是设计意图——违约出售是"绝境求生"（明天交不起房租），不是获利手段。问题是设计文档 Section C 中的"场景二"只提到了赔钱的后果，但没有给出具体的盈亏计算，玩家在做决策时缺乏经济信息。

例外情况：如果物品是 JACKPOT（perceivedValue 低，realValue 高），违约出售可能盈利。但这属于"贪婪捕食"场景，不是"绝境求生"。

**建议**:
1. 在违约出售 UI 中明确显示净利润/亏损预估
2. 设计文档中补充"违约出售通常亏损"的说明，强调这是救命手段而非获利手段
3. 考虑将赔偿推迟到客户实际来赎时才结算（当前代码似乎已经这样做），而非出售时立即扣除

**严重程度**: :green_circle: 低 -- 经济逻辑自洽，但需要更好的文档说明和 UI 反馈

---

### 12. 警察调查概率与清白值的交互缺少极端场景防护

**问题**: 议价系统文档定义警察调查每日 15% 基础概率，清白值 < 30 时 +10%（共 25%）。但连续持有赃物的累积被查概率很高。

**分析**:

持有一件赃物 N 天后至少被调查一次的概率：

| 持有天数 | 基础(15%) | 高风险(25%) |
|---------|----------|------------|
| 1 天 | 15% | 25% |
| 3 天 | 39% | 58% |
| 5 天 | 56% | 76% |
| 7 天 (标准期限) | 68% | 87% |

在标准 7 天典当期限内，即使基础概率 15%，也有 68% 的概率被调查。如果玩家持有多件赃物，每件独立判定，被查概率更高。

后果是：赃物没收 + 声誉惩罚。如果玩家以低价收了赃物（低风险），7 天后有 68% 概率血本无归。

从经济角度：
```
收赃期望收益 = 绝当变现 * (1 - 调查概率) - 当金 * 调查概率
            = realValue * 0.32 - principal * 0.68  (基础概率7天)
```

盈利条件：`realValue * 0.32 > principal * 0.68`，即 `principal < realValue * 0.47`

这意味着如果当金低于真实价值的 47%，收赃在统计上是有利可图的。但考虑到清白值 -2/-3 的惩罚和归零 Game Over 风险，实际 ROI 远低于此。

**建议**: 当前数值使收赃成为极高风险操作，这可能是设计意图。但建议在设计文档中补充"收赃经济分析"表，帮助策划理解调优空间。如果 15% 被认为太高（68%/7天），可以考虑降到 8-10%。

**严重程度**: :green_circle: 低 -- 数值上自洽，但缺乏策划可用的经济分析

### 13. 包干制利息在 0% 义举合同下的特殊情况

**问题**: 0% 利率 + 包干制 = 永远零利息。但续当时收取的利息也是 0，玩家完全无收益地延期。

**分析**:

```
0% 义举合同：
- 签约利息 = principal * 0% * 7/7 = $0
- 赎回总额 = principal + $0 = 只还本金
- 续当利息 = principal * 0% = $0
```

从玩家经济角度，0% 义举合同的唯一收益是声誉（人情+1 或+2）。但如果 NPC 请求续当且玩家同意：
- 玩家收到 $0
- 资金继续被占用 7 天
- 人情 +5（按设计文档）或 +1（按声誉系统文档）

如果初始资金 $10,000，每日支出 $50，每周医药费 $1,000：
- 7 天支出 = $50 x 7 + $1,000 = $1,350
- 如果义举合同本金 $2,000 被占用 14 天（一次续当），玩家损失 $2,000 流动性

这在经济上非常痛苦，但也是设计意图："慈善有代价"。

**建议**: 当前设计自洽。但建议在 UI 中显示续当 0% 合同时的特殊提示："本次续当不收取利息，你的资金将继续被占用。"

**严重程度**: :green_circle: 低 -- 设计自洽，仅需 UI 提示优化

## 亮点

### :star: 包干制利息设计的经济优雅性

包干制利息是整个经济系统中最精妙的设计。它用一个极简的机制（签约时锁定利息）同时解决了三个问题：
1. 消除玩家-NPC 利益对立
2. 让"提前赎回"成为正面体验（资金回笼快）
3. 让利息计算对玩家完全透明

从 Sylvester 的优雅性框架看：最小化负担（一个固定数字）+ 最大化力量（改变了整个博弈动态）。

### :star: 强制违约作为"终极道德测试"的经济定位

赔偿金 = 2x principal 的设计将强制违约定位在一个精确的经济甜蜜点：
- 对普通物品（realValue 接近 principal），违约是严重亏损 -- 阻止无脑滥用
- 对 JACKPOT 物品（realValue 远超 principal），违约是巨大诱惑 -- 制造道德困境
- 这种非线性的价值关系确保只有在"发现宝贝"时才会真正面临抉择

### :star: 双路径变现设计（违约出售 80% vs 绝当出售 100%）

区分"急售打折"和"合法持有正常卖"在经济上合理且直觉自然。这个设计让"等绝当"成为经济上更优的选择，但需要承担时间风险（NPC 可能来赎回/续当），创造了有意义的博弈。

9. 强制违约的惩罚力度（-20 还是 -50？）
