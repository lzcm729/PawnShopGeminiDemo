## 发现的问题

### Bug 1: 库存容量限制未在典当时强制执行

- **严重程度:** P1 (严重)
- **问题描述:**
  `getEffectiveInventoryCapacity()` 在 `InventoryModal` 中用于显示容量，但在 `commitTransaction()` 或 `RESOLVE_TRANSACTION` reducer 中没有检查是否超出容量。玩家可能在库存已满时仍然接受新的典当物品。

- **影响范围:**
  - `C:\Users\lzcm7\OneDrive\GameProject\PawnShopGeminiDemo\hooks\useGameEngine.ts` - `commitTransaction()` 函数
  - `C:\Users\lzcm7\OneDrive\GameProject\PawnShopGeminiDemo\store\GameContext.tsx` - `RESOLVE_TRANSACTION` reducer (行322)
  - `C:\Users\lzcm7\OneDrive\GameProject\PawnShopGeminiDemo\components\NegotiationPanel.tsx` - 议价面板

- **问题代码位置 (GameContext.tsx:322):**
  ```typescript
  const newInventory = item ? [...state.inventory, item] : state.inventory;
  // 没有容量检查，直接添加到库存
  ```

- **预期行为:**
  当库存达到上限时，应该禁止接受新的典当物品，或者至少显示警告。

- **实际行为:**
  代码中没有找到容量检查逻辑，可能允许超出容量限制。

- **建议修复方案:**
  1. 在 `NegotiationPanel.tsx` 添加容量检查，当库存已满时:
     - 禁用"接受交易"按钮
     - 显示警告提示 "库存已满，请先清理库存"
  2. 或者在 `RESOLVE_TRANSACTION` reducer 中添加检查:
     ```typescript
     const capacity = getEffectiveInventoryCapacity(state.shopUpgrades);
     const activeCount = state.inventory.filter(i =>
       i.status === 'ACTIVE' || i.status === 'FORFEIT'
     ).length;
     if (item && activeCount >= capacity) {
       // 拒绝添加或触发警告
     }
     ```

### Bug 2: 预约客户生成使用的物品模板有限

- **严重程度:** P2 (一般)
- **问题描述:**
  `customerGenerator.ts` 中的 `itemTemplateIds` 只使用了 `item_watch_gambler` 和 `item_console_student` 两种模板，导致预约客户带来的物品种类单一。

- **影响范围:**
  - `systems/appointment/customerGenerator.ts` 第33-200行

- **预期行为:**
  不同类型的候选应该带来与其背景相符的多样化物品。

- **实际行为:**
  几乎所有候选都使用相同的几个物品模板。

- **建议修复:**
  为每个候选模板配置更多样化的 `itemTemplateIds`。

### Bug 3: 存档兼容性 - pendingAppointedCandidates 可能为 undefined

- **严重程度:** P2 (一般)
- **问题描述:**
  虽然 `LOAD_GAME` reducer 处理了 `pendingAppointedCandidates` 的默认值，但如果旧存档中没有这个字段，在其他地方直接访问可能导致问题。

- **影响范围:**
  - 存档加载流程

- **代码位置:**
  - `store/GameContext.tsx:187`

- **当前处理:** 已有 fallback: `const pendingAppointedCandidates = action.payload.pendingAppointedCandidates || [];`

- **状态:** 低风险，已有基本处理

## 结论

**状态:** 基本通过 (附带改进建议)

**总结:**
典当行升级系统的核心功能实现完整，包括升级购买、效果计算、柜台设施开关、维护费扣除、预约板系统等。代码结构清晰，reducer 和 hook 分离合理。发现一个中等严重的问题（库存容量限制未强制执行）和一个可改进项（预约客户物品多样性）。
