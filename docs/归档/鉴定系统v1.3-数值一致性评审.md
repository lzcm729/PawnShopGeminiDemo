## 发现列表

### 1. 🔴 不确定度等级阈值与代码实现存在两套定义体系

**问题**：设计文档 3.1 节定义了基于 `uncertainty` 数值的三档等级（LOW < 0.10, MEDIUM 0.10~0.20, HIGH > 0.20），但当前代码 `systems/items/utils.ts` 中的 `getUncertaintyRisk` 函数使用的是完全不同的判定逻辑——基于估值区间的 `max/min` 比率（>3.0 为 HIGH, >2.0 为 MEDIUM, 其余 LOW）。

**分析**：这是两个完全不同的度量体系。一个是衰减系数（0.30 初始，每次乘 0.85），另一个是区间端点比率。它们之间不是线性对应关系——由于非对称偏置 (Skew) 的存在，相同的 uncertainty 值可以产生差异很大的 max/min 比率。

数值验证：
- 初始 uncertainty=0.30，对于 realValue=$1000，anchor=$1000 时：width=300，极端 skew=0.2 时范围为 [$940, $1240]（比率 1.32 -> LOW）；skew=0.8 时范围为 [$760, $1060]（比率 1.39 -> LOW）。这意味着即使 uncertainty 处于 HIGH（>0.20），代码中的比率判定也可能返回 LOW。
- 但当 perceivedValue 与 realValue 差距大（如假货：perceived=$8000, real=$200）时，同样的 uncertainty=0.30 会产生巨大的 max/min 比率。

**两套体系产生不同结果的场景很多，实现精度收益机制时必须先统一。**

**建议**：
1. 明确精度收益机制使用 `uncertainty` 数值本身（鉴定文档 3.1 的定义），而非代码中现有的 `getUncertaintyRisk`。
2. 现有的 `getUncertaintyRisk` 改名为 `getBlindPurchaseRisk`，专用于盲收警告（机制 E），因为它基于区间端点比率的判定更适合"玩家看到的信息跨度"。
3. 新增 `getUncertaintyLevel(uncertainty: number): 'LOW' | 'MEDIUM' | 'HIGH'` 函数，直接按 <0.10 / 0.10~0.20 / >0.20 判定，用于精度收益机制。

### 2. 🔴 方向 A 与方向 D 的组合效应可能过强，导致"不鉴定就没法玩"

**问题**：设计文档 3.7 节承认"LOW 不能过强——避免不鉴定就没法玩"，但数值分析显示 LOW vs HIGH 的组合差距非常大：

**方向 A（开价偏移）**：LOW 时 NPC 开价降低 8%，HIGH 时提高 8%。差距 = 16%。

**方向 D（让步幅度）**：LOW 时让步乘以 1.30，HIGH 时乘以 0.70。差距 = 85.7%（1.30/0.70）。

**方向 C（变现偏差）**：LOW 期望偏差 0%，HIGH 期望偏差 -10%。

**组合极端场景量化**（假设物品 realValue=$1000, NPC Floor=$700）：

| 维度 | 全鉴定 (LOW) | 不鉴定 (HIGH) | 差距 |
|------|-------------|-------------|------|
| NPC 开价 | $920 (x0.92) | $1080 (x1.08) | $160 |
| 侮辱线 | $416 (Floor x0.7 x0.85) | $539 (Floor x0.7 x1.10) | $123 更窄的安全区 |
| 每轮让步 (CALM, 10%剩余) | 39 (30 x 1.30) | 21 (30 x 0.70) | 近 2 倍差距 |
| 流当变现 | $1000 (0%偏差) | $900 (期望-10%) | $100 |
| **总经济影响** | **全面优势** | **全面劣势** | **$383+ 综合差距** |

对于 $1000 的物品，综合经济差距约 $380+（占物品价值 38%）。这已经超过了合同档位选择带来的影响（0%~20% 利率差距），使得鉴定投资几乎成为"必选"而非"策略选择"。

**分析**（理论支撑）：
- Schell 的 Triangularity 原则要求：安全选项（盲收）的期望回报应该合理但较低，风险选项（鉴定投入 AP）的期望回报应较高但有不确定性。当前设计中，盲收几乎是"纯劣势"而非"低回报的安全选项"。
- Sylvester 的弹性挑战 (Elastic Challenge) 要求不同程度的投入都有意义。如果不鉴定就"全方位受罚"，等于否定了盲收策略的存在价值。

**建议**：
1. **降低方向 D 的幅度**：将 LOW/HIGH 从 x1.30/x0.70 调整为 x1.15/x0.85，使差距从 85.7% 收窄到 35.3%。让步是概率性事件，乘数过大会导致体验方差极端化。
2. **或者将 MEDIUM 设为默认基准而非惩罚**：当前设计中 MEDIUM 是"正常玩"，HIGH 是"受罚"。考虑将 HIGH 改为 x0.85（轻微劣势）而非 x0.70（重度劣势），使盲收成为"略亏但可接受"的策略。
3. **保持方向 A 和方向 C 不变**：这两个方向的数值幅度合理（A 的 +-8% 和 C 的偏差都在可感知但不压倒的范围内）。

### 3. 🟡 uncertainty 衰减数学与 LOW 阈值存在"甜蜜陷阱"

**问题**：文档 3.1 注释称"纯靠收窄需约 7 次鉴定才能达到 LOW"，但实际数学计算为：

```
初始: 0.30
第1次: 0.30 x 0.85 = 0.255
第2次: 0.255 x 0.85 = 0.217
第3次: 0.217 x 0.85 = 0.184  -> MEDIUM
第4次: 0.184 x 0.85 = 0.156  -> MEDIUM
第5次: 0.156 x 0.85 = 0.133  -> MEDIUM
第6次: 0.133 x 0.85 = 0.113  -> MEDIUM
第7次: 0.113 x 0.85 = 0.096  -> LOW!
```

确实需要 7 次才能达到 LOW（<0.10），文档描述准确。但更重要的问题是：

- 达到 MEDIUM（<0.20）只需要 **3 次鉴定**
- 从 MEDIUM 到 LOW 需要额外 **4 次鉴定**
- 在 10 AP/天的预算下，花 7 AP 在一个物品上意味着其他 3 个客户（4 客户/天）几乎无法鉴定

**分析**：这构成了一个"甜蜜陷阱"——玩家在第 3 次鉴定后进入 MEDIUM（已经不错了），但为了追求 LOW 的 30% 让步加成，可能会贪心地继续鉴定 4 次以上，耗尽 AP 预算。这在策略上可能是有趣的权衡，但也可能让玩家感到"MEDIUM 不够好"的焦虑。

**建议**：
1. 在文档中明确 MEDIUM 是"够用"的标签，强调 3 次鉴定的 ROI 拐点。
2. 考虑在 UI 中的商人直觉里加入"差不多看清了"（MEDIUM）vs"完全掌握了"（LOW）的差异化文案，让玩家理解 MEDIUM 也是值得的。
3. 或者调整衰减系数为 0.80（而非 0.85），使 LOW 在 5~6 次即可达到，减少过度投资的诱惑。

### 4. 🟡 FAKE/JACKPOT 发现时 uncertainty 直降 0.10 与精度收益联动的矛盾

**问题**：文档 3.1 提到"发现 FAKE/JACKPOT 特征时 uncertainty 直接降至 0.10（LOW）"。但这与精度收益机制存在逻辑冲突：

- 发现 FAKE 时，物品估值已经崩塌，此时方向 A（开价偏移）和方向 D（让步幅度）的加成是否还有意义？NPC 的 Ask 和 Floor 已经被重置为低值。
- 发现 JACKPOT 时，物品估值已跳升，玩家处于信息优势，LOW 的加成会进一步放大玩家的优势位——这是否过于慷慨？

**分析**：
- FAKE 场景：uncertainty 降至 0.10 -> LOW -> 开价 x0.92 + 让步 x1.30。但 FAKE 已经将 NPC 的 Ask/Floor 重置为极低值，此时 LOW 的精度加成几乎是"锦上添花"——玩家在 FAKE 场景下已经完全掌控局面，不需要额外精度加成来帮忙。
- JACKPOT 场景：玩家发现了一个被低估的宝物，精度收益的"卖出保障"（方向 C：0 偏差）让玩家可以稳定以高价变现，这进一步强化了捡漏的收益。但文档 3.7 的约束 4 声称"特征发现仍是最大奖励"，这意味着 LOW 的额外加成不应"喧宾夺主"。

**建议**：
1. 对于 FAKE 场景：uncertainty 降至 0.10 合理（玩家确实看清了物品），但在文档中备注"方向 A 和 D 的加成效果在 FAKE 场景下实际影响有限，因为 Ask/Floor 已被重置"。
2. 对于 JACKPOT 场景：考虑将 uncertainty 降至 0.15（MEDIUM 偏下）而非 0.10，避免方向 C 的"零偏差变现"让捡漏利润过于稳定。**捡漏的核心乐趣是"发现价值"，而非"无风险套利"**。

### 5. 🟡 方向 C（流当变现偏差）与经济参数文档的"绝当变现比例 80%"存在叠加歧义

**问题**：经济参数文档定义"绝当变现比例 = 80%（真实价值的 80% 快速变现）"。而鉴定文档 3.4 定义的变现偏差公式为：

```
变现价值 = realValue x (1 + 偏差)
```

但当前代码实现（`usePawnShop.ts` 第 350 行）中，流当变现直接使用 `item.realValue`（100%），没有应用 80% 折扣。

**两个问题**：
1. **80% 折扣和方向 C 偏差如何叠加？** 如果两者同时生效：LOW 时变现 = realValue x 0.80 x 1.0 = 80%；HIGH 时变现 = realValue x 0.80 x (1 + random(-0.30, +0.10))，期望值 = 72%。这使得 HIGH 的惩罚从"期望亏 10%"变成"期望亏 8%（相对于 80% 基准）"——差距被压缩了。
2. **代码实际用的是 100% realValue**，与经济参数文档的 80% 不一致（这是独立于鉴定系统的 bug，但影响方向 C 的设计前提）。

**分析**：方向 C 的设计意图是"精度保障变现收益"。如果最终实现中流当本身就已经是 100% realValue（如代码所示），那么方向 C 的 HIGH 偏差（期望 -10%）就成了唯一的变现惩罚来源，其重要性会更高。反之，如果叠加 80% 折扣，方向 C 的边际影响会被稀释。

**建议**：
1. 首先统一经济参数文档与代码实现的基准变现比例（80% 还是 100%？）。
2. 方向 C 的偏差公式应明确写为：`变现价值 = realValue x 基准变现比例 x (1 + 偏差)`，确保与基准比例的叠加关系清晰。
3. 如果保留 80% 基准，建议将 HIGH 的偏差范围从 [-30%, +10%] 放大到 [-35%, +15%]，以维持方向 C 在叠加后的可感知性。

### 6. 🟡 方向 A 的侮辱阈值偏移可能与代码中的 BehaviorTag 侮辱修正产生冲突

**问题**：鉴定文档 3.2 (A2) 定义侮辱线修正：

```
实际侮辱线 = npcFloor x 0.7 x 侮辱修正系数
```

但当前代码中，侮辱阈值的计算方式是：

```typescript
// useNegotiation.ts
baseThreshold = 0.7
// 叠加 BehaviorTag 修正（DESPERATE: -0.10, STUBBORN: +0.10 等）
insultThreshold = minPrincipal x (threshold after mods)
```

```typescript
// fillerGenerator.ts
baseInsultThreshold = baseMinimum x 0.70
// 再叠加 BehaviorTag 乘性修正
```

这里有两个问题：
1. **鉴定精度的侮辱修正系数如何与 BehaviorTag 修正叠加？** 设计文档没有指定叠加顺序。
2. **两处代码中侮辱阈值的计算基准不一致**：`useNegotiation.ts` 用 `minPrincipal x threshold`（加性修正），`fillerGenerator.ts` 用 `baseMinimum x 0.70` 再乘性修正。当精度修正加入时，需要明确它是应用在哪一步。

**建议**：
1. 在设计文档中明确完整公式：`实际侮辱线 = npcFloor x 0.7 x BehaviorTag修正 x 精度修正`（三者独立相乘）。
2. 确认代码中统一使用一处计算逻辑，避免 `useNegotiation.ts` 和 `fillerGenerator.ts` 各自维护一套侮辱阈值。

### 7. 🟡 方向 D 的让步幅度乘数与议价系统中的"让步幅度"定义存在歧义

**问题**：鉴定文档 3.3 定义：

```
实际让步幅度 = 基础让步幅度 x 精度乘数
```

但议价系统中的"让步幅度"有两种含义：
1. **`concessionRatio`**（设计文档 4.1）：占剩余空间的比例（5%/10%/15%）
2. **`concessionAmount`**（代码实现）：实际金额 = 剩余空间 x concessionRatio

精度乘数应该作用在哪一个？
- 如果作用在 `concessionRatio` 上：LOW 时 CALM 的比率从 10% 变成 13%（乘以 1.30），这是"比例放大"。
- 如果作用在 `concessionAmount` 上：LOW 时让步金额直接乘以 1.30，这是"金额放大"。

**分析**：由于 concessionRatio 已经是对剩余空间的比例，两种方式在数学上等价（concessionAmount = remainingMargin x concessionRatio x precisionMultiplier = remainingMargin x (concessionRatio x precisionMultiplier)）。所以实际上不影响结果。但为了实现清晰性，应在文档中明确。

**建议**：在设计文档中将公式细化为：
```
concessionAmount = (currentAsk - npcFloor) x concessionRatio x 精度乘数
```
消除歧义。这虽然是"无害歧义"（结果相同），但在后续实现时有助于代码审查。

### 8. 🟡 首次出价的让步概率乘子与设计文档不一致

**问题**：议价设计文档 3.5 定义首次出价时"NPC 让步概率 = 基础概率"，但代码实现 (`pushPull.ts` 第 93-94 行) 中首次出价的让步概率是 `基础概率 x 0.3`（70% 折扣）。

| 来源 | 首次出价让步概率 |
|------|-----------------|
| 议价设计文档 3.5 | 基础概率（无折扣） |
| 代码实现 | 基础概率 x 0.3 |

对于 CALM 型 NPC：设计文档预期首次出价 25% 让步概率，代码实际为 7.5%。差距极大。

**分析**：这虽然不是鉴定系统本身的问题，但当精度乘数叠加到让步幅度上时，基础让步概率的偏差会放大整体经济影响。如果首次出价的让步概率本身就很低（7.5%），那么方向 D 的精度乘数（x1.30 vs x0.70）对实际让步金额的影响也会打折——因为 NPC 大概率根本不让步。

**建议**：
1. 统一设计文档与代码的首次出价让步概率。如果 x0.3 是有意设计（首次出价 NPC 通常不轻易让步），则更新设计文档。
2. 注意：精度乘数只影响让步幅度，不影响让步概率（文档 3.3 已明确）。但两者的组合效果需要在模拟中验证。

**建议**：统一取一种方案。推荐使用代码的线性方案（更简洁、更易理解），并更新设计文档。

### 10. 🟢 格物系统的"估价锁定"与鉴定精度收益的交互需要明确

**问题**：格物系统文档 4.1 说明"白天鉴定的进度自然保留到夜间"，且格物也能收窄估价区间（每次 ~20%，高于白天的 ~15%）。如果物品在夜间格物时 uncertainty 被进一步降低，该值是否影响已成交的精度收益？

文档 3.4 明确了"记录时机：在成交时记录当前 uncertainty 等级（uncertaintyAtDeal）"。这意味着**格物对已成交物品的方向 C 没有影响**——方向 C 使用成交时快照。

但对于**未成交**的物品（如玩家白天鉴定了但没有当天完成交易，第二天客户可能回来），格物对 uncertainty 的降低是否会影响第二天的方向 A 和 D？

**分析**：这是一个边界设计问题。如果物品在夜间格物后 uncertainty 降低，第二天同一客户回来时应该享受更低的 uncertainty 带来的精度收益。这在逻辑上是合理的（"我昨晚仔细研究了一下这个东西"）。

**建议**：在文档中补充说明：
- 方向 A 和 D 使用**实时 uncertainty**（鉴定+格物累积降低后的值）
- 方向 C 使用**成交时快照 uncertainty**（uncertaintyAtDeal）
- 这允许"白天粗看 + 晚上精研 + 第二天稳赚"的长线策略

### 11. 🟢 特征发现概率的"基础 50%"与鉴定系统文档的"~20%"描述不一致

**问题**：经济参数文档定义特征发现基础概率为 50%（difficulty=0 时），而鉴定系统文档（格物系统表 4.1 也引用）多处描述"每次鉴定 ~20% 概率发现特征"。

实际上两者不矛盾：50% 是 difficulty=0 时的理论上限，大多数特征有 difficulty > 0。例如 difficulty=1.0 时概率为 20%，这与文档描述一致。但 difficulty=0 的特征（最容易发现的）有 50% 概率，远高于"~20%"的一般描述。

**建议**：在鉴定文档中注明"~20% 为中等难度特征的典型概率；简单特征（difficulty=0）可达 50%"，避免读者误解。

### 12. 🟢 方向 A 的"NPC 对话态度"列表目前无数值锚点

**问题**：文档 3.2 (A3) 列出了 4 种 NPC 风格在 LOW/HIGH 时的行为变化（如"狡猾型 LOW 时放弃演戏"），但这些仅是定性描述，没有量化指标。

**分析**：这不是严重问题——态度变化主要通过文案和对话表现，不需要精确数值。但"放弃演戏"是否意味着 SLY 型的 Ask 虚高程度降低？如果是，这就与方向 D（让步幅度乘数）产生重叠效应。

**建议**：明确 A3 是**纯叙事层**的表现变化，不影响任何数值参数。避免未来实现时有人把"放弃演戏"实现为 Ask 降低——那应该由方向 A1（开价修正系数）统一处理。

### 13. 🟢 耐心消耗概率化后与鉴定 AP 消耗的竞争资源关系需要 ROI 验证

**问题**：代码中推拉区的耐心消耗已从"每轮固定 -1"改为概率制（basePatienceLossChance: 0.45~0.85），但鉴定的耐心消耗仍然是固定 1/次（经济参数文档第 98 行）。

这意味着鉴定的"客户耐心成本"是确定性的，而推拉的"客户耐心成本"是概率性的。在 AP 有限的情况下，玩家面临的权衡是：

```
鉴定 1 次 = 1 AP + 1 耐心（确定消耗）+ 信息收益
推拉 1 轮 = 0 AP + 0~1 耐心（概率消耗）+ 价格推进
```

如果耐心资源非常稀缺（如强硬型只有 3 点），花 2 点在鉴定上（确定消耗）只剩 1 点给推拉，而推拉每轮可能不消耗耐心（15%~55% 概率不消耗），这使得"少鉴定多推拉"可能成为优势策略。

**分析**：这实际上是一个有趣的策略空间，但需要确认它是有意设计的。如果鉴定的精度收益（方向 A+D 的加成）能弥补 2 点耐心的损失，那么权衡是有意义的。

**建议**：这是一个需要 playtest 验证的平衡点，暂不建议修改数值，但建议在设计文档的 3.8 节（策略深度）增加"耐心预算"作为权衡因素。

---

## 亮点

### ⭐ 三方向时间序列设计（A-D-C）是出色的体验架构

精度收益沿时间轴分布——议价开始即时兑现（A）、推拉过程渐进兑现（D）、流当结算延迟兑现（C）——这是优秀的体验设计。它满足 Schell 的兴趣曲线原则：玩家在每个阶段都能感知到鉴定投资的回报，而不是"鉴定了半天最后也不知道有什么用"。

### ⭐ "精度乘数只影响让步幅度，不影响让步概率"的分离设计

这一设计保持了社交博弈（NPC 是否让步取决于互动质量）与专业能力（你多懂行）的独立性。符合 Sylvester 的决策设计原则：不同维度的决策应产生不同类型的影响，而非混在一起。

### ⭐ 方向 C 的"成交时快照"设计规避了后悔机制

如果方向 C 使用实时 uncertainty（即流当时的值），玩家可以在成交后通过夜间格物来降低 uncertainty，从而"挽救"一笔草率的交易。这会破坏"鉴定投资"的前置承诺感。"成交时快照"确保了决策后果的不可逆性。

### ⭐ 参数汇总表和策略深度分析提升了文档可用性

v1.3 新增的 3.7 和 3.8 两节为实现者和测试者提供了清晰的参照基准，是前次评审中缺失的重要内容。

## 总体评价

鉴定系统 v1.3 的精度收益机制在**概念层面**是优秀的——它成功地将"信息就是金钱"的核心主题量化为三个方向的经济影响，并沿时间轴分布以创造持续的正反馈。这解决了前次评审中"鉴定只给信息但不影响机制参数"的核心问题。

然而在**数值层面**存在两个需要优先处理的问题：

1. **severity: 🔴 高** — 不确定度等级的定义在设计文档（基于 uncertainty 数值）和代码（基于区间比率）之间不统一。实现精度收益机制之前必须解决。

2. **severity: 🔴 高** — LOW vs HIGH 的组合效应可能过强（约 38% 物品价值的差距），有"不鉴定就没法玩"的风险。建议调低方向 D 的幅度（从 +-30% 降至 +-15%），或者将 HIGH 的惩罚减弱。

其余 🟡 中等发现主要是设计文档与代码实现之间的数值不一致（#8 首次出价概率、#9 坚持加成），这些应在精度收益机制实现前统一，以确保新旧系统在同一数值基准上运行。

🟢 低等发现多为边界情况的明确性问题，不影响核心体验，但值得在文档中补充说明以避免实现偏差。

**整体评级**: 概念优秀，数值需要校准。建议在实现前先解决 #1（统一定义体系）和 #2（组合效应过强），然后进入 playtest 验证阶段。

---

> 本评审基于 Schell 的 Triangularity 平衡理论（安全/风险选项的期望回报应可比较）、Sylvester 的 Skill Range 分析（不同投入程度都应有意义）、以及 Rouse 的"玩家能动感"原则（玩家的策略选择不应被单一最优解主导）。
