# 洞察系统 v1.1 — 系统间交互与冗余评审

> **评审日期**: 2026-02-07
> **评审对象**: `洞察系统 (Customer Insight System).md` v1.1
> **评审视角**: 系统间交互与冗余 (Integration)
> **关联文档**: 鉴定系统 v1.7 | 议价谈判系统 v1.4 | 人物能力升级系统 v1.1 | 格物与精魄系统 v1.0

## 发现列表

### 1. 🟡 洞察系统与"共情"技能的信息层级重叠未明确边界

**问题**：洞察系统定义了三层信息输出（心理倾向 / 底线暗示 / 道德信息），而人物能力升级系统中灵韵 T1"共情"技能的效果是"使用洞察系统时，同样 1 AP 可多揭示一层信息"。但洞察系统文档中完全没有提及共情技能的存在，也没有说明"多揭示一层"的具体含义——是从两层变三层？还是基础只给一层？

**分析**：洞察系统文档（第 2 节）描述的三层信息（心理倾向、底线暗示、道德信息）看起来是一次性全部展示的（从 UI 呈现的弹窗来看，三层同时出现）。如果基础版一次展示全部三层，那"多揭示一层"就无效果可言。反过来，如果基础版只展示部分信息，洞察系统文档就缺少了这个关键的分层展示规则。

两份文档对同一机制的预设不一致，实现时必然产生歧义。

**建议**：在洞察系统文档中明确"基础展示层级"和"共情增强后展示层级"。建议方案：
- 基础洞察：展示第一层（心理倾向）+ 第二层（底线暗示）
- 持有共情后：额外展示第三层（道德信息）
- 在文档第 2 节或第 3 节中添加"与共情技能的交互"小节

### 2. 🔴 洞察的"底线暗示"与鉴定精度收益的信息输出存在功能重叠

**问题**：洞察系统第二层信息"底线暗示"告诉玩家客户底价的大致范围（veryLow / low / medium / high 四档），而鉴定系统的精度收益机制（第 3 节）通过 uncertainty 影响 NPC 开价、侮辱线、让步幅度等参数。两个系统都试图解决同一个问题——帮助玩家估算"安全出价区间"。

**分析**：从信息论角度看：
- **鉴定精度** 提供的是关于**物品价值**的信息，间接影响议价行为（开价修正、让步幅度）
- **洞察底线暗示** 提供的是关于**客户底价**的信息，直接提示底价范围

表面上看两者的信息对象不同（物品 vs 人），但从玩家决策角度看，两者都服务于"我应该出多少钱"这同一个决策。当玩家既做了充分鉴定（低 uncertainty，开价修正有利）又使用了洞察（知道底价范围），信息冗余可能削弱两者各自的价值感。

更关键的是：底线暗示给出的是 `底价/期望价` 比例的定性描述（< 50% / 50-75% / 75-90% / > 90%），而议价系统中 NPC 的 `minimumAmount` 本身就是隐藏的底价。洞察的底线暗示本质上在部分"泄露"`minimumAmount` 的信息，但鉴定精度收益是通过修改系统参数来体现信息价值。两种信息兑现方式不一致。

**建议**：
1. 明确两者的**决策时序**和**互补关系**：洞察在议价前使用，提供"人"的信息用于合同档位选择；鉴定精度在议价中生效，影响推拉过程的系统参数。在洞察文档中添加一段说明两者的互补逻辑。
2. 考虑让底线暗示与鉴定精度产生交互效果——例如"低 uncertainty + 洞察"时底线暗示更精确（从四档变为更细的定性描述），使两者投资有叠加回报而非独立冗余。

### 3. 🟡 洞察的"心理倾向"与议价系统的"NPC 推拉风格"概念重叠

**问题**：洞察系统定义了四种心理倾向（绝望 / 坚定 / 虚张声势 / 真诚），而议价系统定义了四种 NPC 推拉风格（HARD / SOFT / SLY / CALM）。两者都是对 NPC 谈判行为的分类。

**分析**：对比两套分类系统：

| 洞察-心理倾向 | 对应 BehaviorTag | 议价-推拉风格 | 映射关系 |
|-------------|-----------------|-------------|---------|
| 绝望 | DESPERATE | SOFT | 高度对应 |
| 坚定 | STUBBORN | HARD | 高度对应 |
| 虚张声势 | SUSPICIOUS, SAVVY | SLY | 高度对应 |
| 真诚 | NAIVE, SENTIMENTAL | CALM | 部分对应 |

两套分类体系使用不同的命名和不同的映射键（BehaviorTag vs 推拉风格），但描述的是同一个 NPC 维度的信息。玩家通过洞察看到"坚定"，和在议价中发现对方是"HARD"型，获得的信息本质相同。

问题在于：**BehaviorTag 到推拉风格的映射关系在任何文档中都没有被明确定义。** 这是一个跨系统的未文档化假设——洞察系统假设 DESPERATE 意味着可以激进压价，议价系统假设 SOFT 型让步概率高。但两者之间的等价关系全靠实现时的隐含约定。

**建议**：
1. 创建一份明确的 `BehaviorTag → 推拉风格 → 心理倾向` 三方映射表，放在议价系统或核心设定文档中。
2. 洞察系统文档第 2B 节的表格应增加一列"对应推拉风格"，使读者立刻理解心理倾向的机制含义。

### 4. 🔴 洞察系统的道德信息来源与事件链系统的数据依赖未被事件链文档承认

**问题**：洞察系统第 2D 节声明从三个数据源提取道德信息：`dialogue.pawnReason`、`chainState.variables`（如 hope）、`item.name + 情感标签`。但洞察系统的关联文档列表中未包含事件链系统，且事件链系统文档中也未提及洞察系统会读取 `chainState.variables`。

**分析**：这是一个**单向依赖**——洞察系统依赖事件链系统的数据，但事件链系统不知道有消费者。如果事件链系统重构变量命名（例如 `hope` 改为 `hopeLevel`）、改变变量语义、或添加新的变量类型，洞察系统的道德信息生成逻辑就会默默失效。

此外，`dialogue.pawnReason` 属于 NPC 生成系统的数据（由 Gemini API 或 fallback 生成），这个依赖也没有在洞察文档中明确。生成系统可能产生的 pawnReason 格式和内容并不确定，洞察系统如何从自由文本中"提取"道德信息？是直接显示原文还是进行映射？

**建议**：
1. 洞察文档第 9 节"相关文档"应增加事件链系统的引用。
2. 事件链系统文档应在其数据接口部分声明"洞察系统会读取 chainState.variables 中的 hope 等字段"。
3. 明确 `dialogue.pawnReason` 的处理方式：是原文展示还是通过模板映射。如果是原文展示，需要考虑 AI 生成文本的质量控制。

### 5. 🟡 洞察系统与格物系统在"夜间信息获取"维度的关系未定义

**问题**：格物系统（第 4 节）定义了夜间格物可以收窄估价区间（~20%/次）和发现特征（~25%概率），与白天鉴定功能重叠但效率略高。洞察系统只能在白天（议价阶段）使用。但当格物系统在夜间完成了物品的完整鉴定（甚至顿悟解锁全部信息）后，第二天面对同一客户赎回时，玩家已经拥有了物品的完整信息，此时洞察系统的"看物 vs 看人"的资源竞争是否仍然有效？

**分析**：洞察系统的设计初衷强调"与鉴定形成互补"和"资源竞争"。但格物系统的存在削弱了这个竞争——如果玩家在夜间已经通过格物完成了物品鉴定，白天的 AP 就不需要再投入鉴定，可以"免费"使用洞察。AP 的竞争关系从"鉴定 vs 洞察"变成了"洞察 vs 其他白天行动"。

这不一定是问题——也可能是格物投资的合理回报。但洞察文档第 3C 节的"与鉴定的资源竞争"表格完全没有考虑这个情况，显示文档对格物系统的交互是盲区。

**建议**：在洞察文档第 3C 节的资源竞争表中，增加一行描述格物已完成物品鉴定时的场景：
```
| 已夜间格物（物品已知） | 无需白天鉴定，AP 可用于洞察 | 格物投资的回报 |
```

### 6. 🟢 洞察的 BehaviorTag 映射假设与 NPC 生成系统的一致性风险

**问题**：洞察系统假设每个客户都携带 `behaviorTags` 数组，且标签属于 {DESPERATE, STUBBORN, SUSPICIOUS, SAVVY, NAIVE, SENTIMENTAL} 六种之一。但客户生成系统（Gemini API）可能生成不在此集合中的标签，或多个冲突标签同时存在的情况。

**分析**：洞察文档第 2B 节的心理倾向映射表假设一个客户只有一种倾向。但实际数据可能包含多个 BehaviorTag（例如示例 3 中客户同时拥有 SAVVY 和 SUSPICIOUS）。当多个标签分属不同倾向时（例如 STUBBORN + DESPERATE），系统应该选择哪一种倾向作为输出？这个优先级规则缺失。

**建议**：在第 2B 节添加多标签冲突解决规则，例如：
- 按优先级排序：DESPERATE > STUBBORN > SUSPICIOUS/SAVVY > NAIVE/SENTIMENTAL
- 或取第一个匹配的标签
- 同时明确 fallback：当所有标签都不在已知列表中时，默认使用"真诚"

### 7. 🟡 洞察系统与人物能力系统"洞若观火"技能的功能边界模糊

**问题**：人物能力系统中的融合技能"洞若观火"（旧影+灵韵 T1）在议价开始时自动感知客户赎回意愿（高/中/低），并在赎回意愿低时显示流转估值范围。能力系统文档在 4.6 节中专门声明"与洞察系统的区分：洞察揭示客户当前状态，洞若观火预测未来行为"。

但从玩家感知角度看，两者都是"看人"的信息输出，且都在议价开始时提供。洞察给出心理倾向（当前）和底线暗示，洞若观火给出赎回意愿（未来）和流转估值。

**分析**：能力系统文档虽然做了区分声明，但洞察系统文档完全没有提及洞若观火的存在。这意味着：
1. 如果玩家同时使用洞察 + 拥有洞若观火技能，UI 上需要同时展示两套信息面板，但两份文档都没有描述这个叠加 UI 的呈现方式。
2. 洞察消耗 1 AP，洞若观火是被动免费触发。信息获取成本不一致，可能导致洞若观火严格优于洞察（免费获取更有经济决策价值的信息）。

**建议**：
1. 洞察文档应在"相关文档"或"与核心愿景的契合"中增加与洞若观火的关系说明。
2. 考虑 UI 整合方案：洞若观火的信息可以作为洞察面板的"第四层"展示（被动追加），而非独立面板。这样在叙事上形成"共情让你看见现在，阅历让你看见未来"的递进感。

### 8. 🟡 洞察系统耐心消耗"已禁用"但议价系统未同步

**问题**：洞察文档第 3B 节明确说明"当前实现中所有性格的耐心消耗均为 0"，保留了设计值作为未来参考。但议价系统文档中未提及洞察操作对耐心的影响（或不影响）。

**分析**：议价系统第 3.4 节详细定义了每轮出价的耐心消耗概率模型，但在"消耗来源"的完整性上有盲区——没有提到洞察操作是否独立于推拉轮次计耐心。如果未来洞察恢复耐心消耗，议价系统的耐心经济模型就需要重新平衡。

更重要的是，鉴定系统的"客户不耐烦"意外（H 节，骰子 16-25）会导致额外耐心 -1，但仅在鉴定 2+ 次时触发。洞察不计入"鉴定次数"，但消耗的是同一个 AP 池和同一个客户的时间。这里隐含了一个规则假设：洞察不触发"客户不耐烦"事件。

**建议**：
1. 洞察文档中明确声明"洞察不计入鉴定次数，不触发鉴定意外事件表"。
2. 议价系统文档中补充"非推拉操作的耐心影响"小节，列出鉴定、洞察等操作对耐心的影响规则。

### 9. 🟢 "攻心"技能的效果描述与洞察第三层道德信息的叙事矛盾

**问题**：人物能力系统中"攻心"技能利用对方心理弱点压低底价，其设计意图是"心理操控"。而洞察系统的第三层"道德信息"的设计目标是"让玩家在压价时清楚知道后果"——即产生道德阻力。

**分析**：如果玩家同时使用洞察（看到"她女儿生病了"）和攻心（利用心理弱点降低底价），叙事上是否应该产生更强的道德冲突反馈？当前两个系统各自独立运行：洞察给信息，攻心给机制效果，但没有交叉产生情感加倍的设计。

从 Sylvester 的"机制即叙事"理论来看，如果洞察和攻心能产生交互效果（例如使用洞察后再使用攻心时，商人直觉文案变为更痛苦的内心独白），就能将两个独立系统编织为统一的情感体验。

**建议**：这是一个增强型建议，非必须修复。可在洞察文档或议价文档中添加设计备注：
> "若玩家已使用洞察揭示道德信息，后续使用攻心技能时，商人直觉文案应引用已知的道德信息，加强道德张力（如'你知道这笔钱是她女儿的药费。你还是利用了她的绝望。'）。"

### 10. 🔴 底线暗示的"底价/期望价比例"计算基准未在议价系统中定义

**问题**：洞察系统第 2C 节的底线暗示矩阵使用 `底价/期望价` 比例作为行维度（veryLow < 50%, low 50-75%, medium 75-90%, high > 90%）。但"期望价"这个概念在议价系统中存在歧义：
- `desiredAmount`（NPC 期望金额）= 客户生成时的数据
- `npcAsk`（NPC 当前要价）= 推拉中动态变化的值
- `askPrice`（初始要价）= 可能受鉴定精度修正影响的值

**分析**：洞察文档使用 `desiredAmount` 作为"期望价"（从文案示例可推断），但议价系统 v1.4 引入了推拉机制后，`npcAsk` 会在推拉过程中动态变化。洞察在议价期间使用时，如果玩家已经推拉了几轮导致 `npcAsk` 下降，此时底线暗示的基准应该用初始 `desiredAmount` 还是当前 `npcAsk`？

如果用 `desiredAmount`，暗示内容是静态的，不反映推拉进展。如果用 `npcAsk`，暗示内容会因推拉进度而变化，但洞察限制为每客户 1 次，不存在二次使用的场景。因此实际问题更细——玩家在推拉的哪个阶段使用洞察会影响底线暗示的语义。

**建议**：在洞察文档第 2C 节明确计算基准：
```
底线暗示比例 = minimumAmount / desiredAmount
```
使用生成时的 `desiredAmount`（而非动态的 `npcAsk`），因为暗示反映的是客户的原始心理状态，不因推拉进展而变化。

### 11. 🟡 洞察系统的 CSV 数据文件路径与数据驱动架构的一致性

**分析**：从项目的数据驱动架构来看（CLAUDE.md 中明确：内容在 `assets/data/*.csv`，机制在 TypeScript），洞察系统的数据分离是符合架构规范的。但需要确认：
1. 当前 `assets/data/` 目录中已有 `Items_Base.csv` 和 `Traits.csv`，`InsightHints.csv` 是否已创建？
2. CSV 格式是否在某处有 schema 定义？洞察文档给出了矩阵结构但没有明确 CSV 的列定义（哪些列、什么分隔符、编码格式）。

**建议**：
1. 在文档第 8 节"数据文件"中增加 CSV 格式说明（列名、分隔符、编码）。
2. 验证 `InsightHints.csv` 是否已存在于代码库中，如果不存在则标记为待实现。

### 12. 🟢 洞察系统缺少与"因果自见"技能的命运预兆在 UI 上的协调说明

**问题**：因果自见技能（人物能力系统 4.6 节）在议价阶段提供合同档位的命运预兆色彩（金色/暗红），而洞察系统在议价阶段提供心理倾向 + 底线暗示 + 道德信息面板。当两者同时生效时，玩家面对的信息密度可能过高。

**分析**：从 Schell 的兴趣曲线理论来看，议价阶段本身已是微观兴趣曲线的高峰期（出价 -> 推拉 -> 成交），叠加洞察面板 + 因果自见的色彩暗示 + 商人直觉文案 + 鉴定精度相关直觉文案，玩家需要同时处理的信息通道过多，可能破坏专注的议价体验。

这不是洞察系统本身的缺陷，而是多系统叠加后的涌现问题。

**建议**：考虑在未来的 UI 设计阶段，建立"信息呈现时序表"——定义议价阶段各信息源的显示优先级和时序：
1. 进入议价 -> 洞若观火自动触发（如有）
2. 玩家点击洞察按钮 -> 洞察面板弹出
3. 悬停合同档位 -> 因果自见色彩显示
4. 出价后 -> 商人直觉文案
5. 推拉过程 -> 精度相关直觉

### 13. 🟡 洞察系统未定义与"施压"/"攻心"技能的使用顺序交互

**问题**：人物能力系统中，施压和攻心技能都在议价阶段使用（消耗 1 AP），洞察也在议价阶段使用（消耗 1 AP）。三者共享 AP 池。但洞察文档没有定义使用顺序对效果的影响。

**分析**：考虑以下场景：
- 玩家先洞察（看到客户是"绝望型"，底线远低于期望价），然后再使用攻心（利用心理弱点）。
- 玩家先攻心（底价已被降低 10%），然后再洞察——此时底线暗示反映的是攻心前的原始比例还是攻心后的新比例？

如果底线暗示使用 `minimumAmount` 的当前值（被攻心修改后的值），那先攻心再洞察会看到一个"更低的底线暗示"（因为 floor 被降低了但 desiredAmount 不变，比例更低了）。这可能在信息上产生误导——玩家会以为"本来底线就这么低"。

如果底线暗示使用原始 `minimumAmount`，那使用顺序无影响，但需要在代码中区分"原始底价"和"当前底价"。

**建议**：在洞察文档中明确声明底线暗示使用**原始底价**（未被技能修改的值），并在数据流设计（第 6 节）中标注此约束。这样洞察始终反映客户的"天然底线"，而施压/攻心是在此基础上的额外操控。

---

## 亮点

- **信息维度的正交设计**：洞察系统（看人）与鉴定系统（看物）的设计初衷形成了优雅的正交互补，两者共享 AP 资源形成有意义的竞争。这是 Sylvester 优雅启发中"与多个系统互动的机制"的良好实践。

- **底线暗示的 4x4 矩阵设计**：将底价比例与心理倾向交叉，形成 16 种不同的暗示文案，用最小的数据结构产生丰富的信息变体。CSV 外部化 + 多变体机制 + 确定性随机选择，是数据驱动架构的典范。

- **道德信息作为第三层的设计层次**：心理倾向（策略信息）-> 底线暗示（经济信息）-> 道德信息（情感信息），形成清晰的信息价值递增和情感递进。这与 Schell 的兴趣曲线理论中"逐步加深"的节奏设计一致。

- **每客户限用 1 次的约束**：简单但有效的设计约束，防止了洞察系统被过度使用而削弱信息获取的资源竞争张力。

## 总体评价

洞察系统 v1.1 在自身设计上是精简且有效的——三层信息结构清晰、与鉴定系统的正交互补关系优雅、数据驱动的文案矩阵实用。作为一个"小而美"的信息系统，它很好地服务了"道德困境"这一核心体验。

但从系统间交互的视角看，该文档存在**三类需要关注的问题**：

**一、单向依赖未被双向确认。** 洞察系统依赖事件链系统的 `chainState.variables`、NPC 生成系统的 `dialogue.pawnReason`、以及 `BehaviorTag` 系统的标签集。这些依赖只在洞察文档中单方面声明，上游系统均未承认有下游消费者。这意味着任何上游重构都可能默默破坏洞察功能。建议对关键依赖建立双向文档引用。

**二、与能力系统的交互规则缺失。** 共情增强、洞若观火、攻心/施压等技能都会与洞察系统产生交互，但洞察文档完全没有提及这些技能的存在。虽然能力系统文档侧做了部分说明，但作为被增强的一方，洞察文档应该至少声明自己是"可被增强"的，并列出增强接口。

**三、计算基准的跨系统歧义。** 底线暗示使用的"期望价"和"底价"在议价系统的推拉机制中是动态变化的值，在施压/攻心技能中是可被修改的值。洞察文档需要明确锚定于哪个时间点的哪个数值，否则实现时的隐含假设将成为 bug 的温床。

总体而言，建议下一版本（v1.2）重点补充系统交互边界的明确定义，并与人物能力系统文档进行对齐更新。
