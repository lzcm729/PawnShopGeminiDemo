# 物品变体与标签系统 (初稿) -- 系统间交互与冗余评审

> **评审日期**: 2026-02-07
> **评审对象**: `物品变体与标签系统 (Item Variant & Tag System).md` 初稿
> **评审视角**: 系统间交互与冗余 (Schell Lens #9 Elemental Tetrad / Lens #10 Holographic Design)
> **评审员**: Game Designer Agent

---

## 发现列表

### 1. 🔴 Trait 系统与 Tag 系统的概念重叠 -- 两套"物品属性"体系并存

**问题**：当前项目中存在两套独立的物品属性机制：**Trait 系统**（鉴定系统中的 FLAW / STORY / FAKE / JACKPOT / STOLEN，定义于 `ItemTrait` 接口）和**Tag 系统**（本文档中的 G1 状态组 / G2 材质组 / G3 本质组，定义于 `ItemTag` 类型）。两者在功能上存在严重重叠：
- FAKE（Trait）与 FAKE_HISTORY（Tag）都描述"伪造"属性
- FLAW（Trait，如"划痕"、"非原装"）与 BROKEN / DIRTY / RUSTED（G1 State Tag）都描述物品的负面物理状况
- JACKPOT（Trait）与 IMPERIAL / CELEBRITY（G3 Essence Tag）都指向"高价值发现"

**分析**：从 Lens #9（元素四象限）角度看，这两套系统分属不同的设计时期 -- Trait 服务于白天鉴定/议价的信息博弈机制，Tag 服务于夜间格物/修复/重铸的加工机制。但它们描述的是**同一个现实域**（物品的属性和状况），却使用了完全不同的数据结构、不同的术语、不同的发现方式。这违反了信息源唯一性原则：同一件物品的"破损"状况，可能同时表达为 Trait `FLAW:"非原装表带"` 和 Tag `BROKEN`，两者的价值影响如何叠加？谁先谁后？玩家看到的是哪个？

从代码实现来看（`systems/items/types.ts`），`Item` 接口已经同时承载了 `hiddenTraits/revealedTraits`（Trait 系统）和 `tags`（Tag 系统），但两套数据之间没有定义任何映射或互斥规则。

**建议**：
1. 明确定义 Trait 和 Tag 的**边界**：Trait 是"鉴定发现的信息碎片"（面向白天议价），Tag 是"物品的持久状态标记"（面向夜间加工和价值计算）。两者是不同层级，不应描述同一属性。
2. 建立**单向映射规则**：发现特定 Trait 时，是否应同步添加/移除 Tag？例如，发现 `FAKE` Trait 后，是否应给物品添加某个 Tag 以影响夜间系统的行为？
3. 在本文档第 5 节"与其他系统的接口"中，增加"与鉴定系统 Trait 体系的关系"章节，明确声明两者的分工和交互协议。

### 2. 🔴 价值计算存在两条独立管线 -- 可能产生矛盾结果

**问题**：本文档第 4 节定义的价值计算公式为：

```
最终价值 = 基础价值 x Prod(所有激活标签的价值系数)
```

但在鉴定系统中，物品的价值体系是：`realValue`（真实价值）/ `perceivedValue`（感知价值）/ `currentRange`（估值区间）。这两条管线如何协调？

具体矛盾场景：
- 一件怀表的 `realValue = 1000`，通过鉴定收窄后玩家大致知道值 $900-$1100。
- 夜间修复移除 `BROKEN` 标签后，按 Tag 系统公式：`baseValue x 1.0 = baseValue`（假设 baseValue = 1000）。
- 但 `realValue` 字段是什么？还是原来的 1000 吗？还是需要重新计算？
- 如果重铸注入 `IMPERIAL` (x10)，`realValue` 变为 10000，那鉴定系统的 `uncertainty` 要重置吗？`currentRange` 要重新生成吗？

**分析**：物品的"真实价值"概念在两个系统中有不同的计算逻辑。Tag 系统用乘积公式从 `baseValue` 动态计算；鉴定系统有一个静态的 `realValue` 字段。修复/重铸后，`realValue` 必须同步更新，否则黑市系统（使用 `realValue` 计算价格）、议价系统（基于 `realValue` 设定 NPC 底线）都会产生错误结果。

**建议**：
1. 明确声明：`realValue` 是 Tag 系统公式的**输出结果**，不是独立存储的静态值。每次 Tag 变化时必须重新计算并更新 `realValue`。
2. 在本文档中增加"价值同步协议"章节，定义以下规则：
   - 修复后：`realValue = baseValue x Prod(剩余标签系数)`，`uncertainty` 保持不变（物品本质未变），`currentRange` 按比例缩放。
   - 重铸后：`realValue = baseValue x Prod(新标签系数)`，`uncertainty` 重置为高值（物品本质已变，需重新鉴定），`currentRange` 重新生成。
3. 考虑将 `baseValue` 定义为唯一的"物品固有价值锚点"，所有系统均从 `baseValue + tags` 推导出 `realValue`。

### 3. 🟡 G1 状态标签声称"互斥" -- 但与代码实现的 `tags[]` 数组结构不一致

**问题**：本文档 2.1 节明确说明 G1 状态标签"通常同一时间只存在一种主状态（或无状态）"。但代码实现中（`Item.tags?: ItemTag[]`）是一个普通数组，没有任何互斥约束。同时，`MINT` 被定义为"无负面标签时的默认状态"，但代码中 `MINT` 是一个显式的 Tag 值，需要主动添加。

**分析**：当前设计文档描述了互斥性规则，但这个规则完全依赖实现层的自律。如果修复操作移除了 `BROKEN` 但忘记添加 `MINT`，或者某个 NPC 带来的物品同时被标记了 `BROKEN` 和 `DIRTY`（这在现实中完全合理 -- 一个又脏又破的东西），系统会如何表现？

**建议**：
1. 重新审视 G1 的互斥性假设。现实中一件物品完全可以同时是"破损"和"脏污"的。如果确实需要互斥，需要在文档中明确声明**为什么**要互斥（是简化考虑还是设计选择），并指定当多个负面状态共存时的合并规则。
2. 如果 `MINT` 是"无负面标签的默认状态"，建议将其从 Tag 枚举中移除，改为计算属性：`isMint = tags.filter(isStateTag).filter(isNegative).length === 0`。这避免了"忘记添加 MINT"的错误。
3. 明确 `BROKEN + DIRTY` 共存时的价值系数叠加规则（是相乘还是取最低？）。

### 4. 🟡 变体优先级顺序与文档自身矛盾

**问题**：文档 3.2 节的优先级顺序为：
1. 重铸态 (Essence) -- 最高
2. 破损态 (State - Negative) -- 次高
3. 修复态 (State - Restored)
4. 默认态 (Default)

但文档紧接着的描述说"如果御用怀表被砸烂了，它首先看起来是'烂的'"。这意味着**破损应该高于重铸**，与排列顺序矛盾。

同时，代码实现 (`ItemVariant.priority: number`) 使用数字优先级，注释说"重铸态 priority 100+，破损态 priority 50-99"。这与文档描述的"破损覆盖重铸"的意图相反 -- 数字越大优先级越高，重铸 100 > 破损 50。

**分析**：这是一个典型的文档与实现的未对齐问题。设计意图是"破损覆盖一切"（因为一个砸烂的东西首先看起来是烂的），但优先级数值定义却让重铸覆盖破损。

**建议**：
1. 明确设计意图：如果"砸烂的御用怀表"应该显示为"破损"状态，那么破损态的优先级必须高于重铸态。调整优先级数值为：破损态 100+，重铸态 50-99。
2. 或者，如果重铸态确实应该是最高优先级（意味着即使砸烂了也显示为"御用品"），则修正文档中"被砸烂了首先看起来是烂的"这段描述。
3. 无论哪种选择，都需要在文档和代码中保持一致。

### 5. 🟡 知识池（格物系统）与标签变化的规则缺失

**问题**：格物系统文档 (3.A) 明确说明知识池"ID 不变，总量不变：即使修好（变体改变），知识不会凭空增加"。但本文档中没有明确这一规则，而格物系统文档也没有讨论**重铸后**知识池的行为。

具体未定义场景：
- 一件怀表知识池 100/100，玩家格物到 50/100 后进行重铸（注入 `IMPERIAL`）。物品变成了"宫廷御用怀表"。此时知识池还是 50/100 吗？
- 格物系统说"由 G2 材质/属性标签决定产出类型"。重铸只改变 G3 标签，不改变 G2 标签，所以产出类型不变 -- 但重铸后的物品叙事上已经是完全不同的东西了（"宫廷御用怀表"），继续从中提取"旧影"在叙事上是否合理？

**分析**：格物系统的知识池设计假设了"物品本质不变"，但重铸行为恰恰改变了物品本质。两个系统对"物品本质"的定义存在隐含冲突。此外，格物系统文档 10.3 提到"只有未被完全榨干的物品，才能作为重铸底材"，这条规则只在格物系统文档中提及，本文档没有引用。

**建议**：
1. 在本文档第 5 节增加"与格物系统的知识池交互"，明确说明：重铸后知识池是否保留、是否重置、产出类型是否变化。
2. 将"未被完全榨干才能重铸"这条规则同步写入本文档或重铸系统文档，避免规则散落。
3. 考虑从叙事角度给出合理解释：例如"重铸消耗了物品的部分灵性（知识池减少 X%），但注入了新的本质"。

### 6. 🟡 "所有权判定"规则与典当业务系统的定义不完全对齐

**问题**：本文档 5.2 节定义了所有权判定规则：
- 修复 (A->B)："同源变体"，客户认可，允许赎回。
- 重铸 (A->C)："质变标签"，客户不认可，触发违约赔偿。

但典当业务系统中的违约处理有多种路径（赎回 / 续当 / 强制违约 / 违约出售），且违约赔偿的计算基数是"200% 当金（principal）"。本文档没有说明重铸触发的赔偿是否使用相同的计算公式，也没有说明重铸违约对三维声誉的具体影响。

**分析**：典当业务系统 2.E 节定义了强制违约的声誉影响为"人情-15, 商誉-10, 清白-5"。但重铸导致的"原物灭失"在道德性质上与"强制违约扣留原物"有本质区别 -- 前者是"我把你的东西改造了"，后者是"我不想还你"。使用相同的惩罚值是否合理？

**建议**：
1. 在本文档中明确重铸违约的赔偿公式（是否与强制违约相同的 200% 当金？）。
2. 考虑为重铸违约设计独立的声誉影响参数，或在此文档中明确声明"复用典当业务系统的违约逻辑"并引用具体条款。
3. 增加重铸违约的叙事分歧描述（老兵发现勋章被改造 vs 老兵发现勋章被扣留，情感反应应该不同）。重铸系统文档中有一段精彩的叙事描写（"你毁了它！那上面的刻字是我战友的名字！"），但本文档作为接口层没有引用。

### 7. 🟡 G2 材质标签与现有物品 Category 字段的冗余

**问题**：当前代码中 `Item` 接口已有 `category: string` 字段（如 "古董"、"艺术品"、"珠宝"、"手表"），黑市系统基于 category 生成收购标签。本文档引入的 G2 材质/属性标签（GOLD / MECHANICAL / ARTISTIC / VINTAGE_REAL / SENTIMENTAL / TRENDY）与 `category` 存在信息重叠：
- category "手表" 大概率对应 G2 标签 `MECHANICAL`
- category "古董" 大概率对应 G2 标签 `VINTAGE_REAL`
- category "艺术品" 大概率对应 G2 标签 `ARTISTIC`

两者都试图回答"这件物品本质上是什么类型的东西"，但粒度不同。

**分析**：从 Lens #10（全息设计）角度看，理想状态是每个数据字段都有唯一的职责。`category` 是粗粒度分类（用于 UI 分组、黑市收购筛选），G2 Tag 是细粒度属性（用于格物产出计算）。一件手表可能既是 `MECHANICAL` 又是 `GOLD`，这比 category 更灵活。但两者的关系需要明确 -- G2 tag 是否应该从 category 自动推导？还是完全独立配置？

**建议**：
1. 在本文档中明确 `category` 与 G2 标签的关系：category 是"商品分类"（面向展示），G2 Tag 是"材质属性"（面向机制）。一件物品可以有多个 G2 Tag 但只有一个 category。
2. 定义默认映射规则（如 category "手表" 默认附带 `MECHANICAL`），允许个别物品覆盖。
3. 评估黑市系统是否应从 category 标签切换为 G2 Tag 标签进行收购匹配，以实现标签体系的统一。

### 8. 🟡 G3 本质标签 `TRENDING` 与 G2 属性标签 `TRENDY` 概念模糊

**问题**：G2 中有 `TRENDY`（潮流物品，属性标签，不可移除），G3 中有 `TRENDING`（潮流热点，本质标签，可通过重铸注入）。两者在语义上极为相似，但分属不同标签组。

**分析**：一件物品可以同时是"潮流物品"（天生属性，如限量球鞋）和"潮流热点"（因为某个事件突然火了）。设计文档中对这两个标签的区分不够清晰。从玩家视角看，"TRENDY"和"TRENDING"几乎是同义词，可能造成理解困难。

**建议**：
1. 重新命名以拉开语义距离。例如 G2 `TRENDY` 改为 `POP_CULTURE`（流行文化物品），或 G3 `TRENDING` 改为 `HYPED`（炒作热点）。
2. 在文档中增加对比表格，明确两者的差异：一个是"物品的天生属性"（如球鞋本身就是潮流品类），另一个是"市场赋予的临时价值"（如某个事件导致这件东西突然升值）。

### 9. 🟢 变体映射系统没有定义"修复+重铸叠加态"的变体

**问题**：文档给出了四种变体状态（默认态/破损态/修复态/重铸态），但没有讨论"修复后再重铸"或"重铸后被破坏"等叠加场景下的变体文案。

**分析**：从流程上看，一件物品可能经历 `破损 -> 修复 -> 重铸` 的完整生命周期。修复态变体（"精工润滑的怀表"）在重铸后会被重铸态变体（"宫廷御用怀表"）覆盖，这由优先级规则处理。但如果一件"宫廷御用怀表"后来又被标记为 `BROKEN`（例如某个事件导致物品损坏），应该显示什么变体？是"破损的宫廷御用怀表"还是"停摆的旧表"？

**建议**：
1. 在变体配置中增加"组合态"变体的设计说明。至少需要 `broken_reforged` 变体（如"残碎的御用怀表 -- 曾经辉煌的做工仍然依稀可见"）。
2. 或者，在文档中明确声明"重铸后物品不会再进入破损状态"（即重铸是终态），简化状态空间。

### 10. 🟢 价值系数的极端叠加未做上限约束

**问题**：文档第 4 节的乘积公式 `最终价值 = 基础价值 x Prod(所有标签系数)` 在极端情况下可能产生失控的数值。例如：`IMPERIAL (x10) + LIMITED (x?) + CELEBRITY (x?)` 三个 G3 标签叠加，可能将 $1000 的物品推到 $100,000 以上。

**分析**：虽然 G3 标签通常由重铸注入且需要消耗大量点数，但文档没有定义 G3 标签之间是否互斥。如果允许一件物品同时拥有多个 G3 标签（通过多次重铸或特殊事件），价值可能指数级膨胀，破坏经济平衡。

**建议**：
1. 定义 G3 标签的互斥或数量上限规则（如"一件物品最多拥有 1 个 G3 标签"）。
2. 或者设定最终价值的硬上限（如 `min(乘积结果, baseValue x 20)`）。
3. 在本文档或经济参数文档中补充极端情况的数值验算。

### 11. 🟢 日志系统对标签变化事件的记录未定义

**问题**：库存物品日志系统定义了多种日志类型（ENTRY / REDEEM / FORFEIT / SOLD / INFO / APPRAISAL），但没有"TAG_CHANGE"或"WORKSHOP"类型。当物品经历修复或重铸时，日志系统应该如何记录这些变化？

**分析**：日志系统的设计初衷之一是"玩家操作痕迹"（维度 C），修复和重铸是玩家对物品的核心操作，应该留下记录。例如："Day 5: 你花了一整晚修复这块表的机芯，它终于又开始走了。" 或 "Day 8: 你将金手镯改造成了唐代金镶玉镯。你对自己的手艺感到满意...或者说，心虚。"

**建议**：
1. 在本文档中定义"标签变化时应向日志系统发送事件"的接口规范。
2. 建议新增日志类型 `WORKSHOP`，记录修复/重铸操作的时间、消耗和结果。
3. 这些日志在叙事上特别有价值 -- 如果老兵来赎回时，玩家可以翻看日志回忆"我对他的勋章做了什么"。

### 12. 🟢 `CURSED` 标签的玩法关联完全未定义

**问题**：G3 标签中 `CURSED`（诅咒）标注为"可能导致持有者厄运（特殊玩法）"，但没有进一步说明。在所有关联文档（格物系统、重铸系统、典当业务系统、鉴定系统）中均未提及 CURSED 标签的具体机制。

**分析**：一个未定义玩法的标签不应出现在初稿的标签表中。它会给实现者造成困惑（"我该怎么处理这个标签？"），也可能让其他系统的设计者做出错误假设。

**建议**：
1. 要么在本文档中定义 CURSED 的具体机制（如"持有 CURSED 物品时，每天有 X% 概率触发负面随机事件"），要么将其标记为"未来扩展"并从当前版本的标签枚举中移除。
2. 如果保留，需要说明它与格物系统的交互（格物诅咒物品是否有特殊效果？）、与重铸系统的交互（能否通过重铸移除诅咒？）。

## 亮点

- **"一个 ID，多种表现形式"的架构思路**非常优雅。通过标签控制逻辑、变体控制显示的分层设计，用最小的数据结构支撑了丰富的物品生命周期表现，符合 Sylvester 的优雅性原则（最大化力量 + 最小化负担）。

- **三组标签的分类设计**（状态/材质/本质）逻辑清晰，每组有明确的玩法关联方向（修复目标/格物产出/重铸注入），形成了完整的"负面修复 -> 中性提取 -> 正面注入"的价值创造闭环。

- **文档中 watch_01 的价值演变示例**（$100 -> $1000 -> $10,000）直观展示了系统潜力，是很好的设计沟通方式。

- **变体的文学性命名**（"停摆的旧表" / "精工润滑的怀表" / "宫廷御用怀表"）完美践行了"标签给系统看，变体给玩家看"的分离理念，确保玩家体验到的是叙事而非数据。

---

## 总体评价

物品变体与标签系统在架构层面是一份思路清晰、直觉正确的设计。它成功地将物品从静态数据变成了动态生命体，为修复/重铸/格物三大夜间玩法提供了坚实的数据地基。标签-变体的分离设计在优雅性上值得肯定。

然而，作为连接多个核心系统的底层基础设施，当前文档**对跨系统交互的定义严重不足**。最关键的两个问题是：(1) Trait 系统与 Tag 系统的概念重叠未被识别和解决，这可能导致后续实现中出现"两套系统各说各话"的混乱局面；(2) 价值计算的双管线问题（Tag 乘积公式 vs 鉴定系统的 realValue/perceivedValue 体系）需要立即澄清，否则修复/重铸后的数值传导会产生不可预测的错误。

建议在推进实现之前，优先解决 #1（Trait vs Tag 边界）和 #2（价值计算管线统一）这两个高优先级问题。其余中低优先级发现可在后续迭代中逐步完善。
